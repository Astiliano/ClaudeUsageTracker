# Optimize: Memory Guard, Idle Weight, Native Density, Scaling Charts — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task by task. Steps use checkbox (`- [ ]`) syntax for tracking. Where a skill says to dispatch `general-purpose`, dispatch the role agent this plan names, without `model` and without `name`.

**Goal:** Build the approved optimize spec in its defined order:
- automatic refreshes hold below a commit-headroom floor;
- closing to the tray destroys the WebView;
- the UI is a dense native utility;
- the charts scale with the window.

All of it lands on a tauri 2.12 base.

**Acceptance criteria.** Each item passes or fails.
1. Every task's commit passes the four gates (below), with logs in `.claude-work/optimize/logs/`.
2. Every test named in spec §10 exists under that name and passes, or under the name recorded in "Deviations" below.
3. Spec §1 goals 1-6 are each covered by a passing automated test or by a passing manual check M1-M9 (Task 22). The map is in "Self-review".
4. `Cargo.lock` resolves tauri 2.12.x, tauri-runtime-wry ≥ 2.12.1 and wry ≥ 0.56.1, each exactly once.
5. `package.json` has no `@fontsource/*` dependency.
6. The `hostile-reviewer` whole-plan review after Task 22 returns 0 Critical and 0 Important.

**Architecture.**
- Memory hold:
  - A new `memory.rs` owns the Windows commit-headroom reading and the child peak reading behind one `MemoryProbe` seam.
  - `Machine::decide` takes a `Facts` struct and gains rule 5b, a hold that only automatic triggers see.
  - The driver reads the probe at decide time and before every spawn inside a cycle.
  - The sampler re-checks the floor on every tick and wakes the driver, level-triggered, once memory recovers.
- Window lifecycle:
  - Closing to the tray lets Tauri destroy the window, and `ExitRequested` keeps the process alive.
  - A tray click or a second launch rebuilds the window from config on the async runtime.
  - `tauri-plugin-window-state` keeps the geometry.
- Frontend:
  - TS constants own every shared length and reach CSS through custom properties set by `shellStyle(zoom)`.
  - The history chart height is computed by the pure `chartHeightPx` and applied by a thin `useChartHeight` hook.

**Tech stack.** Rust 2021 (rust-version 1.96), Tauri 2.12, tokio 1, sysinfo 0.39, windows-sys 0.61, rusqlite 0.40, tracing 0.1; React 19 + TypeScript, Vite, vitest (node environment).

**Spec:** `docs/superpowers/specs/2026-10-06-optimize-design.md`. Rulings: `.claude-work/optimize/review/RULINGS.md`. Brief: `.claude-work/optimize/BRIEF.md`.

## Test-environment caveats

1. **Real memory figures.**
   - No driver test depends on this machine's free commit:
     - driver_loop tests build their probe with `FakeMemory::new()`, which reads `Some(u64::MAX)` until a test scripts it (Task 9);
     - driver.rs unit tests use a local `AmpleMemory` (`Some(u64::MAX)`);
     - sampler_loop tests use `FakeMemory`.
   - Only these `cfg(windows)` smoke tests read real OS figures:
     - `available_commit_bytes_reads_a_positive_figure`;
     - `process_peak_of_this_process_is_positive`;
     - `a_finished_run_reports_a_peak`;
     - `a_cycle_reports_a_peak`.
   - Each asserts only `> 0` or `Some`. They hold on any Windows machine with a pagefile or RAM headroom. A failure there is a real FFI defect, not flakiness.
   - The test machine runs about 12 sessions against a ~70 GB commit limit. That is why no driver test may read the real figure: with the 1536 MB default floor, a low-commit moment would turn an automatic-trigger test into a hold.
2. **The fake_claude harness.**
   - `src-tauri/src/bin/fake_claude.rs` reads the process-wide environment variables `FAKE_CLAUDE_MODE` (`emit`, `exit-nonzero`, `slow`, `non-json` and the others listed in that file), `FAKE_CLAUDE_SLEEP_SECS` (default 60), `FAKE_CLAUDE_EXIT`, `FAKE_CLAUDE_STDOUT` and `FAKE_CLAUDE_STDERR`.
   - Every driver_loop test takes `ENV_LOCK` through `EnvGuard` (driver_loop.rs:28-39), a tokio mutex. runner_guard.rs has its own std `ENV_LOCK` (runner_guard.rs:28).
   - Each `tests/*.rs` file is its own process, so the locks never cross files.
   - New tests that set an env var must use the file's `EnvGuard`/`ENV_LOCK`.
   - The peak tests use `slow` with `FAKE_CLAUDE_SLEEP_SECS=2` (spec §10), inside the 5 s timeout of `defaults()`.
3. **Timing.**
   - `defaults()` in tests has `interval_secs: 10` and `timeout_secs: 5`.
   - Exactly two tests wait on a real Timer: `a_held_final_poll_keeps_the_gate_active_until_it_runs` (Task 10) and `a_cut_closing_cycle_keeps_the_gate_active` (Task 11), about 10 s each.
   - Every other wait is a polling loop bounded at 10 s, or the 100 ms negative window of spec §10. Never a bare sleep used as a barrier.
4. **Heap cap and parallelism.**
   - vitest and `tsc` run under the session's `NODE_OPTIONS` heap cap, which is never raised.
   - Run one gate at a time and one test command at a time. This machine is shared and memory-bound.
5. **vitest has no DOM** (`environment: "node"`, `vitest.config.ts`).
   - Hooks and components have no automated test, as the spec §12 residue accepts. Their wiring is covered by the M checks.
   - A test that touches `window` must not construct browser-only state. Task 16 adds a parameter seam for `createMockBackend`.

## Sequence and rejected alternatives

**Order.**
1. Tauri bump (T1).
2. Rust seams (T2-T7).
3. Rust behaviour (T8-T14).
4. Frontend (T15-T20).
5. Docs (T21).
6. Manual verification (T22).

**Rules behind the order.**
- **Seams before behaviour.** The 40-site `Facts` change (T3), the `tests/common` move (T4), the event names (T5), the new Core fields (T6) and the settings key (T7) are each mechanical or narrow. Behaviour tasks then change only logic, and their diffs stay readable.
- **The Rust DTOs come first.** `Dashboard.memory_hold` and `UserSettings.min_free_memory_mb` exist before the TS types mirror them (T16).
  - Between T7 and T16 the UI round-trips the new settings field untyped: Settings.tsx saves `{...settings, x}`.
  - Between T8 and T16 the dashboard carries a field the TS ignores.

**Rejected sequences.**
- **Null sequence.** One commit per spec section, with no seam tasks. The mechanical churn (40 call sites, four Core literals, seven `Driver::new` sites) would sit inside the logic diffs the reviewers must judge. That is the pattern that let per-task reviews approve broken work in the evidence CLAUDE.md cites.
- **Frontend first.** The TS types would mirror Rust shapes that do not exist yet. mockBackend would validate a field that the real backend rejects.
- **Window lifecycle before the sampler cadence.** The destroy path would leave the sampler at 5 s with no window, and the kick would have no consumer. Task 14 depends on Task 13.

**Interim states, all green and behaviour-preserving.**
- **T3 to T9.** The production decide passes `available_commit_bytes: None, memory_floor_bytes: 0`.
  - Rule 5b does not exist until T8, and from T8 on, `None` fails open.
  - Nothing holds until T9 wires the real reading.
- **The send condition.** commands.rs:367 switches to `driver_relevant_changed` in T10, with the driver's settings arm.
  - If it switched in T7, a floor-only change would reach the old arm, which always calls `reset_all_backoff`.
- **`FakeMemory`.** It enters `tests/common` in T9, the first task with a consumer, so no common item is unused.
- **The grid gap.** `GRID_GAP = 8` and the CSS reads of `var(--grid-gap)` land in one task (T17), so the TS constant and the CSS never disagree in any commit.
